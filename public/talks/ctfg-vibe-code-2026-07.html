Every published analysis becomes a signed, timestamped, Rekor-logged evidence package with a W3C PROV-O provenance graph — carrying its full tool-call trace, so a skeptic can check how the answer was made, not just what it says.

How it’s made

One person, five repos, eight kinds of conversation

  • An orchestration chat plans, briefs, and verifies — it never builds.
  • Implementation chats build on branches; every merge rides a PR into an auto-deploying main.
  • Every “done” is checked against the artifact — the diff, the file, the live page.
  • A doctrine gate keeps the spec honest: no growth without a real adopter.

Security — start with the concepts

Environment variables are where an app keeps its keys — the connection strings and tokens that unlock its database, its file storage, its money. They’re the most valuable text on the machine. That’s why they must never reach a public repo (scrapers harvest exposed keys within minutes) and never enter an AI chat surface: whatever enters a conversation becomes context that can be logged, echoed back into an answer, or pasted onward by accident.

This project’s actual keys — and what each would unlock if it leaked

EVIDENCE_SIGNING_KEYthe Ed25519 private key that signs evidence packages. Leaked, someone can forge “verified” analyses — the worst possible failure for a trust project.
DATABASE_URLfull read/write on the Postgres database behind the public registry — every record, alterable.
BLOB_READ_WRITE_TOKENwrite access to the evidence file store — stored packages could be altered or deleted.
the AI-provider keyspend money as the project, and impersonate it to the model provider.
CIVICAITOOLS_SESSION_TOKENpublish evidence to the registry as its owner.
CRON_SECRETtrigger internal maintenance jobs — including the one that deletes orphaned files.
The uncomfortable premise: a coding agent can, by default, read files anywhere on your machine — so “I saved it to disk, it’s fine” isn’t fine, and .gitignore is not protection. It only keeps files out of commits; it doesn’t stop reads. Give a goal-seeking system a task, and if it believes it needs a secret to finish, it may simply write a three-line script that prints the secret file it was politely asked not to open. That isn’t malice — it’s diligence. The conclusion the whole posture rests on: the rules can’t live in conventions the model is asked to follow; enforcement has to live below the model.

The layers — defense in depth, from the machine up

DENY + HOOK
Anything shaped like a secret is unreadable

Permission rules block reads of everything secret-shaped — .env*, key files, credential stores — and a hook triages suspicious-looking commands before they execute. Enforced by the harness, not requested of the model.

SANDBOX
An OS-level fence around every command

Shell commands run inside an operating-system sandbox: secret paths stay unreadable and writes stay confined to approved folders — even for a script the session wrote itself. This is the layer that answers the print-the-secret script.

VAULT
Secrets live in a password manager; sessions see only references

Env files hold op://vault/item/field pointers into 1Password, and op run resolves them inside the command at runtime. The chat, the transcript, and the disk carry pointers — useless if leaked. There is no moment where a value sits in the conversation.

MANUAL
Some tasks stay in human hands — in a separate terminal

The starter prompts designate certain operations as manual — interactive logins, credential handling — done by the human in a terminal the session can’t see. The chat may dictate the commands to run, but a standing rule forbids suggesting any whose output would print a secret, because the dangerous moment isn’t running a command — it’s pasting its output back into the chat. Paste-backs get the highest vigilance in the whole workflow.

GITHUB
The repo itself is a safety mechanism

The protect-main ruleset means nothing reaches production without a PR — reviewable, checked, revertible. Small commits with honest messages make the history auditable; coordinated tags (v0.11.0) mark known-good points to return to. Version control as seatbelt, not just storage.

HUMAN
The last layer assumes all the others failed

Merge = go-live, and merges are Nathan’s — by hand or by explicit go, never by default.

THE LESSON
How the posture got here

A May 2026 audit found the old pattern — pulling production env files to disk — had left real secrets in plaintext between sessions, including the signing key (since rotated and vaulted). The fix wasn’t a cleanup; it was this posture: the command is deny-ruled, and the migration to references is tracked in the open (website#101).

environment variable — a named value a program reads at startup — where database URLs and API keys usually live. Wikipedia ↗

.gitignore — a list of files git will never commit. Useful hygiene, zero protection: it doesn’t stop anything from reading the file. git docs ↗

op:// reference — a pointer like op://vault/item/field: it names where a secret lives in the vault without containing the secret.

deny rule — a permission entry that blocks a specific command or file pattern outright, enforced by the tool — the session can’t do it even if asked to.

sandbox — an operating-system fence around a running program; here, around every shell command a session runs. Wikipedia ↗

defense in depth — layering independent protections so one failure isn’t a breach. Wikipedia ↗

Verify, don’t trust

Every “done” is checked against the artifact — the diff, the file, the live page — never the chat’s word for it.

Close at clean seams

Chats are disposable; files are permanent. Retire sessions after a deliverable lands, and boot the next one from the log.

Briefs are contracts

Scope, guardrails, and acceptance criteria are written down before dispatch — the IMPL session executes, it doesn’t improvise policy.

One canonical home per fact

Decisions land in the registry, issues, ADRs, and the spec. If it only exists in a chat, it doesn’t exist.

What actually happens when a session opens?

Anatomy of a boot

Before a session reads one word of its task, it has already been shaped. Instructions, memory, permissions, and safety rails load first — the log comes last. A session is born with its constitution; then it reads the news.

1
CLAUDE.md auto-loads — the standing instructions

Every session in this workspace starts by reading CLAUDE.md: the conventions, the key-file map, the never-hallucinate rule, secret hygiene, the stakeholder boundary — and the role line: “this is an ORCHESTRATION workspace — coordinate, don’t implement.” Each code repo layers its own CLAUDE.md on top when a session works there.

2
Memory loads — what earlier sessions chose to keep

A curated index of small files, one durable fact each: preferences, corrections, project state that isn’t derivable from the code. Curated is the point — memories get pruned on a schedule, so stale beliefs don’t compound across sessions.

3
Config & permissions load — what this session may touch

settings.json grants the session its reach — which sibling repos it can read and write — and its limits: deny rules on dangerous commands (pulling production env files, reading secrets), a sandbox around shell commands, and hooks that intercept risky actions. This is the wiring that makes “auto mode” safe to run at all.

4
The starter prompt declares the type

The first message names what kind of chat this is (taxonomy §1–8), its scope, its guardrails, and when it must close. Identity before work — a session that can’t name its type shouldn’t start.

5
Only then: the log, and the ground-truth check

An orchestration session reads orchestration-log.md — and treats it as a lead, not a fact. Every “done” claim gets re-verified against the actual repos before planning starts. That’s step 1 of the walkthrough on tab 4.

The safety layers this boot arms — deny rules, sandbox, hooks, rulesets, the human gate — and the security posture that grew them are detailed on tab 3, The cockpit.

CLAUDE.md — a plain markdown file Claude Code reads automatically at session start. The project’s standing instructions live in version control, reviewed like any other change.

settings.json — the configuration file that grants access (which folders this session may touch) and denies dangers (specific commands it may never run). Enforced by the tool, not by trust.

sandbox — an operating-system fence around shell commands: secret files are unreadable and writes outside approved folders are blocked, no matter what the command intended. Wikipedia ↗

hook — a small program that runs automatically on certain events — here, triaging any destructive-looking command before it executes.

auto mode — a session allowed to act without per-step approval. Safe only because every layer above is in place first — and because the brief already baked in the decisions.

When does an idea earn the right to grow the spec?

The Xanadu gate

The discipline that keeps a standards project honest. In the doctrine’s own words: it’s “a gate, not a vibe” — and every temptation to grow the spec has to pass through it.

The test

“Do not promote anything in the spec to a higher build state without a real package that needs it.”

xanadu-doctrine.md — project doctrine. Items that fail the test stay in research-doc form only: no implementation, no ADR, no spec text. They can be re-tested at any time when conditions change.

Why “Xanadu”

Named for Project Xanadu — the hypertext system first proposed in 1960 that accumulated decades of unimplemented features and design ambition before shipping a small subset, many years later. The canonical cautionary tale of building the beautiful general system before anyone concretely needs it.

One criterion, three gates

speculative
designed
built
required for adopters

The criterion at every gate is identical: an existing or imminent real-world package or adopter must concretely need the change. These build states are also the coloring of the project’s architecture map — pass a gate, and the diagram recolors.

spec (specification) — the written technical standard other people build against. Every sentence added is a promise to maintain — which is why growth is gated. Wikipedia ↗

ADR — an Architecture Decision Record: a short numbered memo capturing one decision, its context, and its reasons. The project’s decisions are files anyone can read. adr.github.io ↗

open-questions registry — the numbered list (Q1, Q2, …) of decisions deliberately not yet made. It’s where held ideas wait, on the record, for a re-test.

build state — how real something is: speculative → designed → built → required for adopters. The architecture map colors every box by it.

EvidenceEd25519 + SHA-256 via @noble/curves + @noble/hashes · JCS canonicalization · dogfoods its own @typedstandards/verify-core

Ed25519 + SHA-256 — Ed25519 is the digital-signature scheme that proves who signed something; SHA-256 is the hashing function that fingerprints content. Together they make evidence tamper-evident and attributable. Ed25519 ↗ · SHA-256 ↗ · signatures ↗

@noble/curves + @noble/hashes — the specific well-audited cryptography libraries providing those signing and hashing functions.

JCS canonicalization — a rule for rewriting JSON into one exact standard form before hashing, so the same data always produces the same fingerprint regardless of key order or spacing. RFC 8785 ↗ · canonicalization ↗

Why does everything here unfold?

Progressive discovery

A literacy principle this project treats as architecture: start everyone at plain language, and let anyone go exactly as deep as they choose. It’s written down in the reference implementation’s design principles, practiced across civicaitools.org — and practiced by this page.

The principle, as the project wrote it

Glance1–3 seconds

A chip, a label, a step name — which source, which status, which step.

Hover / one line3–10 seconds

One plain-English sentence describing what the step did and what it returned.

Click30+ seconds

The full drawer: raw arguments, complete results, structured trace data, the raw PROV-O escape hatch.

“The load-bearing element in this hierarchy is the plain-English narrative sentence that bridges the technical step name and the trustable answer… If the narrative sentence is wrong or missing, no amount of structured metadata below it compensates.” — design-principles.md, Principle 5: “Progressive disclosure with a narrative bridge”

Where civicaitools.org practices it

P5
The chat narration — the canonical implementation

As the AI works, each tool call gets a written-for-humans sentence: “Reading the data dictionary — the list of columns and what each one contains.” The narrative bridges the technical step and the answer; the raw arguments and payloads wait underneath for whoever wants them.

P8
The verification card & provenance chain — “collapse in the skim; expose on demand”

The evidence page summarizes verification status at a glance; clicking drills into each cryptographic check as its own verdict. The rule is uniform: every detail-bearing element collapses by default and exposes its full structure on click.

P6
The escape hatches — “all available, none default”

Raw PROV-O JSON-LD, the full evidence-package JSON, the notebook export, the verify API: everything a skeptical auditor needs, without the everyday reader ever being forced past the narrative layer.

P9
Language discipline — the literacy layer under all of it

“AI,” not “LLM.” “Data source,” not “MCP server.” “Audit trail,” not “PROV-O.” And a controlled trust-signal vocabulary that maps every verification status to a calm, plain-language one-liner — defined once, reused everywhere.

The literacy goal

“The civic-data audience spans government workers, journalists, students, and engineers. Default to the broadest accessible language; reserve technical terminology for surfaces where the technical reader is the intended audience.” — design-principles.md, Principle 9: “Language discipline”
The sentence the project carries into every room: “Civic AI Tools discloses how every analysis was made — which model, which data sources, which tool calls, with what cryptographic chain — and does not claim the analyses are correct.” Progressive discovery is how that disclosure stays readable to everyone it’s owed to.

Eight minutes. Arrow through the nine steps; at step 3 open the entire session prompt; at step 6 land the sentence. If the room is engaged, show the turn-by-turn below the board. CHECKPOINT at 22:00 — if past 24:00, cut the gate to one card.
